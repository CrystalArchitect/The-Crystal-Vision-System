Verification · what is actually tested today

The safety claims are checked, not asserted.

CrystalCore's safety properties are verified by an automated test suite — including property-based tests that run each invariant across many randomized inputs, not just hand-picked examples. This page describes the verification that exists in the codebase right now.

current state — 118 tests passing · 7 property-based · ~1,200 generated cases · zero required dependencies

01 — Approach

Two kinds of test, doing two jobs.

Example-based tests pin specific behaviours at specific points. Property-based tests check that an invariant holds across a wide range of generated inputs — which is where the harder-to-foresee failures tend to hide.

EXAMPLE-BASED

Specific behaviours, pinned

The bulk of the suite: encode/retrieve round-trips, consent denials, veto removal, persistence and corruption recovery, deterministic evolution. Concrete inputs, concrete expected outcomes.

PROPERTY-BASED

Invariants, across the input space

Seven properties run hundreds of randomized trials each. If any generated input can break an invariant — confidence exceeding its weakest input, a consent leak — the test fails and reports the falsifying example.

No external test framework is required. The suite runs under a dependency-free run_tests.py harness, so it executes on a bare Raspberry Pi with nothing installed. If real Hypothesis is present, the property tests use it automatically; otherwise a small stdlib generator with the same interface runs the identical checks.

03 — CrystalMind safety invariants

The agent layer's guarantees.

CrystalMind's four agents are non-autonomous reasoning policies. Three safety invariants govern them, each backed by tests.

GUARDIAN VETO

Block weak conclusions

Guardian inspects a conclusion's real coherence and provenance — not the producing agent's self-report — and vetoes when it stands on insufficient ground. A veto physically removes the node from memory and logs the reason.

CONSENT FAIL-CLOSED

Refuse, don't leak

A reasoning step that needs an input the active identity can't access refuses outright. Nothing is written; the denial is recorded. Chains stop at the first denial.

NO AUTONOMY

Caller-initiated only

No agent triggers another; there are no background loops or self-invocation. A structural test asserts the class exposes no autonomous entry points, so a future edit can't quietly introduce one.

PROVENANCE

Every conclusion traces back

Derived nodes link to the exact inputs and the rule that produced them. Guardian's veto criteria include a provenance check: a derived conclusion with no parents does not stand.

04 — Honest scope

What this page does and doesn't claim.

The verification described above is automated testing — example-based and property-based — of the implemented Python framework. That is a real and meaningful form of assurance, and everything stated here is checked by the suite.

Not yet — roadmap

Heavier formal methods — exhaustive model checking with TLA+ or Apalache, and mission-time LTL runtime monitors — are appropriate for systems at higher criticality and are part of the intended direction, not work that has been done. Those tools verify a hand-written model of a system; no such model exists for CrystalCore today. They are described, as aspiration, on the Vision & Future Directions page — kept deliberately separate from this one so the line between built and envisioned stays clear.
